## Initial Blocking Finding

### CBI enrichment could combine two rule revisions

The initial fallback accepted the first list record with the requested rule ID
and a non-nil `CBIProfile`, without requiring its numeric `CBIProfileID` to
match the direct GET result. Because the direct GET and paginated list are
non-transactional reads, a concurrent rule change could synthesize a record
containing `cbiProfileId: 7` from the direct response and profile 8 from the
later list response. A duplicate rule ID across pages could cause the same
inconsistency.

Initial verdict: request changes.

## Resolution

The enrichment selector now requires both the rule ID and numeric
`CBIProfileID` to match the direct result. It ignores stale mismatched records,
accepts identical matching duplicates, and fails closed with no enrichment if
matching duplicates carry conflicting profile objects. The selected SDK
profile is copied by value before attachment.

Regressions cover:

- one matching revision;
- a stale revision before a matching revision;
- a stale-only result;
- conflicting matching duplicates;
- identical matching duplicates; and
- a matching profile attached to the wrong rule ID.

During builder verification of the same boundary, an adjacent contract gap was
also closed: errors matching `context.Canceled` or
`context.DeadlineExceeded` now propagate even when the caller context itself
has not yet recorded the error. Ordinary optional-enrichment failures still
preserve the successful direct result. Focused ordinary and race tests cover
the selector, best-effort failure, caller cancellation, and request deadline.
