## Initial Blocking Findings

The reviewers rejected the initial candidate because:

1. `readOnlyHint: true` contradicted an MCP option that could execute arbitrary
   operator-configured `cmd:` provider argv.
2. Catalog-backed tools and raw engine discovery would auto-expose current
   Zidentity data and future catalog/capability additions.
3. Adapter result caps occurred only after current `list` and some `get` paths
   could fully fetch, allocate, project, and serialize a collection.
4. Model-controlled argument and frame sizes were not bounded before engine or
   dependency work.
5. MCP-specific object envelopes, output-schema error variants, duplicate text
   accounting, and protocol-versus-tool error classes were underspecified.
6. D0 was described as accepted while its own review-completion condition was
   unsatisfied.

## Resolution Mapping

Finding:
`cmd:` made the live tool's read-only annotation inaccurate.

Root cause:
the initial design treated arbitrary provider process execution as an optional
operator convenience inside the MCP trust boundary.

Fix:
D12 now prohibits `cmd:` unconditionally, with no MCP override, and D9 makes
that prohibition part of the annotation claim.

Regression test required by D1:
process-level denial with a sentinel-writing provider command.

Verification:
both reviewers closed the finding against `internal/secretref` and engine
effect metadata.

Finding:
the tool/catalog allow-list could widen with the engine.

Root cause:
engine discovery was incorrectly treated as adapter exposure policy.

Fix:
D4 defines a frozen, fixture-backed registry; startup reconciliation fails on
drift; `tools/list`, `server_capabilities`, and `catalog_schema` derive only from
that registry. The initial tenant surface is the exact 23-operation `show`
snapshot and explicitly excludes Zidentity.

Regression test required by D1:
exact pair/tool enumeration, duplicate/drift rejection, and filtered discovery.

Verification:
reviewers independently reproduced the 21/1/1 catalog count and confirmed the
engine's broader raw discovery remains behind the adapter projection.

Finding:
post-collection output limits did not bound collection work.

Root cause:
the current engine fully buffers collections before an MCP adapter can preflight
its result.

Fix:
D1 removes `resource_list` and `resource_get`; only `show`'s one-record behavior
is admitted. Eligibility is based on the operation path, not the catalog shape
default. List/get now require an engine-level bounded collection and pagination
design.

Regression test required by D1:
fakes that fail if any admitted tenant call reaches `List` or `Get`, and exact
one-record assertions for all registered `Show` pairs.

Verification:
reviewers checked browser/reader behavior and accepted the explicitly documented
single-response buffering and oversize-singleton fallback as D1 constraints.

Finding:
inputs, invalid frames, and repeated invalid calls were not bounded early enough.

Root cause:
the initial policy specified an output cap but no strict pre-SDK transport or
separate invalid-message accounting.

Fix:
D10/D14 define a 64 KiB strict frame boundary, UTF-8/duplicate/depth/trailing
checks, enum/field limits, a 100-call admitted-tool budget, and a separate
1000-frame budget charged before validation. Every invalid frame closes the
session without resynchronization.

Regression test required by D1:
each malformed/oversize class with frame budget one must prevent a following
valid handler call; semantic failures must consume the admitted-tool budget.

Verification:
the primary reviewer found the invalid-frame accounting gap on recheck; both
reviewers approved only after the final correction.

Finding:
MCP result, error, and task behavior was ambiguous across protocol versions.

Root cause:
internal engine values were assumed to map directly to MCP, and protocol-level
validation was conflated with tool-execution failure.

Fix:
D8/D9 define per-version fixtures, explicit object success/error envelopes,
schema `oneOf` coverage, canonical duplicate text, complete-result sizing, and
the protocol/tool error split. D6 advertises no task capability and follows
2025-11's requirement to process stray task metadata synchronously without
creating task state.

Regression test required by D1:
schema fixtures and process transcripts for every admitted protocol version,
including invalid arguments and task metadata.

Verification:
the second reviewer caught the task-negotiation mismatch; both reviewers
approved the corrected task and framing delta against official specifications.
