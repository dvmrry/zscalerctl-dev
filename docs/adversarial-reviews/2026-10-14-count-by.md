# Builder Handoff

## Intent

feat(cli): add --count-by for grouped record counts

Three fresh LLM agents drove the CLI against a live non-production tenant
(2026-10-14). To answer "how many members per group", the identity agent paged
35,731 users into context and counted by hand. `--count-by <path>`
(repeatable) counts projected records per value combination and writes
`{"count_by": [...], "records": N, "distinct": N, "counts": [{<path>: value,
"count": N}, ...]}`, largest first. `--limit N` keeps the N largest counts.

A path that reaches a list counts each distinct element once per record, so
counting users by `groups.id` gives members per group. Paths through the same
list read from the same element (`groups.id,groups.name` pairs each group's id
with its own name); only paths on independent branches combine. Rows are
`{"values": {<path>: value}, "count": N}`. A record with no value counts under
`null`. Counting runs on the redacted projection after filters,
so it can only group by values the mode renders. A path the mode omits, or a
secret field, is a usage error (exit 2) before any read, the same rule
`--filter` follows. `--fields` and `--offset` are rejected with `--count-by`.

# Adversarial Review

Fresh-context reviewer: Strata (Qwen3.8-Flash-Next IQ3_S, gm01), read-only, no command execution, 2026-10-14 (round 2)

Baseline used from the supplied inputs: base `9fe71f9`, head `a46a7d7`. No separate process-doc baseline was provided; I treated the round-1 head as the review baseline and reviewed only the fix diff plus the supplied full `internal/resources/count.go`.

## Blocking Findings

None.

I attacked the three prior blockers and did not find a concrete source-verifiable way for the fix to fabricate combinations, drop records, collide row keys, or count under the wrong mode in the changed surface.

Specifically:

- **Multi-path pairing / cross-multiplication:** `pathTuples` groups paths by their first segment and resolves those paths together under the same child. When the child is a list, it iterates list elements and recurses on each element, so `groups.id,groups.name` pairs values from the same element. Paths under different first segments are cross-producted, which is the documented “independent branches combine” behavior. I checked:
  - paths through the same list of objects;
  - nested lists;
  - an empty list;
  - a missing intermediate object;
  - explicit `null` values;
  - a record where one path exists and a sibling path in the same element does not;
  - paths where one path is missing in one element and present in another.
  In these cases the code either produces tuples from the same element or `nil` for missing paths; it does not pair values from different list elements.
- **Row key collision:** `countRow.MarshalJSON` now emits `{"values":{...},"count":N}`. The count key is fixed and nested values are keyed by path. A counted path named `count` or `values` no longer collides with the outer count key.
- **Duplicate paths:** `ValidateCountByPaths` rejects exact repeated paths with `CountByPathError{Duplicate:true}` before counting. The CLI test pins the usage error message.
- **Value identity:** `countKey` now uses JSON encoding, so `1` and `"1"` are distinct group keys. `compareCountValues` now compares numeric values numerically for ordinary numeric types, which addresses the round-1 numeric lexical-order nit.

## Non-Blocking Risks

1. **`compareCountValues` is not a total order for some distinct counted values, so row order can be nondeterministic.**

   - **file/path:** `internal/resources/count.go`
   - **concrete issue:** `countNumber` converts `int`, `int64`, `float64`, and `json.Number` to `float64`. Distinct large `int64` values can map to the same `float64`, e.g. `1000000000000000000` and `1000000000000000001`. When that happens, `cmp.Compare(x, y)` returns `0`, and the function continues to the next value position. If all positions compare equal, it returns `0`. Separately, `1` and `"1"` also compare equal via `FormatProjectedValue` because they are not both numbers. Since rows are collected from a map and sorted with `slices.SortFunc`, which is not stable, distinct rows with equal counts can appear in arbitrary order. With `--limit`, this can make the retained top-N rows nondeterministic.
   - **why it matters:** The output is a machine contract. Grouping identity is now JSON-based, but ordering identity is rendered/float-based. That mismatch can produce flaky goldens and different CLI output between runs for distinct rows that the CLI correctly treats as distinct.
   - **how to reproduce or verify:** Inspect `compareCountValues([]any{int64(1000000000000000000)}, []any{int64(1000000000000000001)})`; it should return non-zero but returns `0` because both convert to the same `float64`. Likewise `compareCountValues([]any{1}, []any{"1"})` returns `0` if `FormatProjectedValue(1)` and `FormatProjectedValue("1")` both render as `1`.
   - **test that would catch it:** Add a table test for `compareCountValues` asserting a non-zero result for distinct large `int64` values and for mixed `1`/`"1"`, or add a `CountProjectedRecords` test with many equal-count large IDs and assert a stable deterministic order. A robust fix is an exact numeric comparator for JSON numbers plus a final deterministic tie-breaker such as `countKey`.

2. **The new `--from-dump` test may not fully pin stored-mode counting unless `country` is mode-specific.**

   - **file/path:** `internal/cli/snapshot_test.go`
   - **concrete issue:** The added test proves that a standard dump rejects `--count-by share_only`. It also proves that a share dump can count by `country`. If the CLI’s default mode when no `--redaction` is supplied is `standard`, and `country` is rendered in `standard`, the second case would also pass even if the count-by check used the default mode rather than the dump’s stored `share` mode. To fully pin stored mode, the test should count by a field whose availability differs between the stored mode and the default mode.
   - **why it matters:** The original blocker was that `--from-dump` counting was not proven to use the dump’s stored mode. A test that passes under both stored-mode and default-mode behavior is a weak pin.
   - **how to reproduce or verify:** Check whether `country` is rendered in both `standard` and `share`. If yes, the second assertion does not distinguish stored mode from default mode.
   - **test that would catch it:** Add `--from-dump shareDir --count-by share_only zia locations list` and assert it succeeds and emits `share_only` values, or use another field that is rendered only in the stored mode and not in the default mode.

3. **`listItems` only recognizes `[]any` and `[]string`.**

   - **file/path:** `internal/resources/count.go`
   - **concrete issue:** If projected records ever contain another slice type such as `[]int`, `[]json.Number`, `[]bool`, or a custom slice type, `listItems` returns false and `pathTuples` treats the list as a scalar. A path ending at that list would emit the whole list as one value instead of one row per element.
   - **why it matters:** Counting semantics for list fields would silently degrade if projection or source decoding ever produces a JSON-like slice type other than `[]any`/`[]string`.
   - **how to reproduce or verify:** Construct a projected record with `tags: []int{1,2}` and count by `tags`. The current code would not expand the list through `pathTuples`’ list branch.
   - **test that would catch it:** Add a `CountProjectedRecords` case for a non-`[]any` slice type, or add a projection invariant test that all list fields are normalized to `[]any`/`[]string`.

4. **The output-safety loop in `count_by_test.go` is broader than needed.**

   - **file/path:** `internal/cli/count_by_test.go`
   - **concrete issue:** The loop skips the `APP_DEV` leak check whenever any argument contains `groups.name`, including cases where `groups.name` is only a filter argument and not a counted path. That weakens the leak check for filter-only cases.
   - **why it matters:** If a future change leaked a filter value into output during a `--count-by groups.id` invocation that also used `--filter groups.name=...`, this loop would not report it.
   - **how to reproduce or verify:** The condition is `strings.Contains(strings.Join(tc.args, " "), "groups.name")`, not a check that `groups.name` is in `--count-by`.
   - **test that would catch it:** Narrow the exception to cases where `groups.name` is actually a counted path, or parse the expected `values` objects and allow only values that appear there.
