# Builder Handoff

## Intent

chore(deps): bump zscaler-sdk-go to v3.8.55; follow the Zidentity move

SDK v3.8.49 renamed `zscaler/zid` to `zscaler/ziam` and moved the Zidentity
admin API from the vanity admin host onto the OneAPI gateway under
`/ziam/admin/api/v1`. The paginator's endpoint constants follow it; the ZPATWO
transport no longer rewrites the vanity admin host (it still rewrites the
token host). For ZPATWO the SDK now targets the ZPA-specific gateway, which is
unverified, so Zidentity on ZPATWO is rejected before authentication, like
gov/govus.

The SDK's `users.Users` now models the full user object. The new fields are
classified (HR attributes and `skipMfaUntil` standard-only; `guest`,
`belongInternalDomain`, `hostedIdp`, `entityType` all modes; `groups` as
`{id, name}` standard-only, a reference to `zidentity/groups`); phones,
postal addresses, display preferences, `manager` and the `loginName` mirrors
are registered as deliberately ignored. Resource-server services gain
`externalName`; `zapsOnboarded` is ignored. `users.Status` is now `*bool`.
Field coverage, the threat-model review stamp, `INSTALL.md`,
`RESOURCE_QUEUE.md` and the Zidentity gap notes are updated.

## Non-Blocking Risks

- `internal/zscaler/reader_zidentity_gov_guard_test.go`: failure messages still
  say “government” even for the `ZPATWO` subtests. This does not affect behavior,
  but it can make a future ZPATWO regression look like a government-cloud issue.
  Verify by grepping the test strings:
  `NewReader(government OneAPI)`, `government Zidentity`, and
  `fixed government session`.

- The ZPATWO guard test uses `resourceZidentityGroups` as the representative
  Zidentity resource. If the guard is product-wide, that is sufficient. If any
  future guard becomes resource-specific, users or resource-servers could bypass
  it. A stronger future test would iterate over the cataloged Zidentity resources
  for `GOVUS`, `gov`, `ZPATWO`, and `zpatwo`.

- The live verification evidence is concrete in the handoff, but no raw operator
  log or dump artifact is attached to this review input. For future audits,
  attaching the operator-run transcript or generated dump artifact would make the
  live proof independently inspectable.

- `zidentity resource-servers list` still fails live with an unclassified
  reason. The handoff says this is pre-existing and not a regression, so it is
  not blocking for this diff. It remains worth tracking because an
  `unknown`/`live_access_failed` classification can hide entitlement, deferred
  resource, or tenant permission issues.
